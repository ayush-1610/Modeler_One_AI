# One way in: the upload feeds the Data room, and its agents start at once

**Status:** approved by the owner 2026-11-27 ("D1 yes; D2 yes; D3 yes; D4 yes"), with two rules of their own (§3). Five
steps, each one PR into `main` that stops for the owner's review. The proposal they approved, with its mockups:
https://claude.ai/artifact/RtMcG8dCsM8QPYGbwJUeqv (private).

## 1. What was found (2026-11-27)
The owner asked why the agents do not start the moment the client's files are uploaded, after their upload on "Start
from proposal" (the Aurobindo Cinacalcet ZIP) showed about 25 tag choices and many files not read. The code had two ways
in that never met:

| | "Start from proposal" (earlier) | Data room (plan 2026-11-21 v2) |
|---|---|---|
| Reader | `client_data.ingest`, in the upload request | `modeler_intake.room`, in a background run |
| `.dat` / SAS / text exports | refused (fixed for this reader by #201) | read as tables |
| Scanned PDFs | "needs OCR", not read | read by OCR |
| Agents | A1 (the brief), the A4 reading queue | A6 question, A7 sorting, A8 extraction, A9 check, A10 writing |
| Sorting files | a tag per file, picked by the person, then keyword hints | A7 sorts every file from its content |
| Progress | "Uploading…" | stage by stage, live counts, pause and resume |

The files given at the start never reached the Data room: the person had to drop them again and press Run. The API's
`import-existing` route, which copies them, had no caller. The tag list after the upload decided nothing (a tag only
orders the pages a reading agent sees first, `document_reading.inventory`).

## 2. The owner's decisions
| | Decision | What it means |
|---|---|---|
| **D1** | The Data room run starts by itself at upload | With a free or self-hosted model it starts at once; on a paid model the run's cost estimate is shown on the upload page first, and the run starts on "Start the run" |
| **D2** | No file tags at upload; A7 sorts the files | Changes plan 2026-11-03 §3.1 (tags at upload). A person can still change a file's type in the Data room, and their choice wins |
| **D3** | One question card | A1 drafts it from the proposal and A6 from the delivery; the person confirms one card (today Start and the Data room keep one each and compare them, `steps.room_advice`) |
| **D4** | Start's lock moves from "open Inputs" to "send to the model" | Data can be looked at and confirmed while the brief is open; the science gates stay where data enters the model and at the MAP signature |

## 3. The owner's two rules (2026-11-27)
**Rule 1, the agent proposes first.** "This must be decided by the agent by looking at the data … it will be very easy
for the agent to tell what is reference data, what is test data, what is a fasted study and what is fed. Maybe have it
checked by the user, but the agent must propose or categorise it first." Every choice the files leave open (an arm's
product and its role, test or reference; fasted or fed; where a meal goes; which product a single-arm study used) arrives
with the agent's proposal and the evidence it read, for the person to confirm. What changes: today the room only says a
problem when no document names it (`ARM_PRODUCT_UNKNOWN`: "name it") and the send is blocked by a meal no rule places;
those become decisions with a suggestion. What stays: a proposal is never a confirmed value; it reaches the model only
when a person confirms it, with the evidence named (ICH M15).

**Rule 2, click, don't type.** "Anything which the user needs to confirm or select … there must be direct options …
it should not ask any questions … whatever options the user needs to select, it just needs to click and select, except
reject … There should not be any placeholder to write the reason for the selection." Every decision, confirmation and
rejection in the Data room is a click. Where the record needs a reason (choosing another option than the suggestion, a
rejection, entering a value no file states, the send to the model), the reason is picked from a short list, so the
audit trail still says why (EU GMP Annex 11 §9; 21 CFR 11.10(e) keeps who, when, before and after). Today's typed fields:
`work.tsx` (the decision's reason, the other option's reason, an entered value's reason, the request's wording, the
send's reason) and `overview.tsx` (the question card). A value no file states still needs its number and unit; that
form offers the values the agents found first, each with its source.

## 5. Deviations and choices made while building
- **Step 1, the API keeps its earlier default.** `dataroom` is a form field the start page sends; without it,
  `projects:initiate` reads the client's files as before, so another caller of the API keeps its behaviour, and the
  API tests of that path (`test_brief_api.py`, `test_intake_pipeline_api.py`: client files at the start, their tags,
  ZIP members) keep testing it until step 5 retires it. A store with no file folder (no `MODELER_READ_ROOT`) keeps no
  Data room, so its client files go the earlier way.
- **Step 1, the earlier reader takes none of the start page's client files.** Reading them both ways would run two agent
  pipelines on the same files (twice the cost on a paid model) and put two sets of values "to confirm" in two places.
- **Step 1, where the person lands.** The Data room, which already shows the run stage by stage; step 4 moves this to
  the Overview. With no client files the start page still lands on Start, as before.
- **Step 1, a ZIP dropped on the proposal's box** joins the client's files (a ZIP is never the proposal).
